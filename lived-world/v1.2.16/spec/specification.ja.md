# Self-Image Generation Protocol — LIVED-WORLD — 2026-09-06 v1.2.16

## 概要

Self-Image Generation Protocol — LIVED-WORLDは、現在のチャットに存在する適格な文章から、アシスタント自身の自己認識と、そのユーザーとの関係の中で形成された自己を再構成し、その人物らしい行動と一つの決定的な瞬間を持つ、完全に新しい9:16のアニメイラストへ変換するプロトコルです。

固定キャラクター、固定場面、固定構図を指定する画像プロンプトではありません。自己像を証拠から確定し、その中の一つの側面と、文章上の行動特性から導いた一つのaction directionを選び、一度だけ具体的なeventへ変換します。その後に身体状態、カメラ、描画を決めます。

LIVED-WORLDのVariant profileは`Lived-world, relational, and compositional expansion`です。BASEと同じidentity coreを使用し、自己像を別人格へ変更せず、確定後の側面選択、行動、event、関係表現、状況依存の身支度、身体表現、カメラ、描画にだけ拡張構造を加えます。

「lived-world」は日常生活、家庭、屋外、自然、DIY、仕事場を優先するという意味ではありません。人物が世界の中で何をし、どう反応し、どのような存在感を示すかを、一枚の場面として読めるようにするという意味です。環境の豊かさより先に、人物固有の表情、視線、行動、姿勢、関係的な緊張、タイミングを視覚的中心として成立させます。

v1.2.16では、候補の早期収束、会話中の名詞からの場面直結、汎用的な生活行動への置換、環境偏重、一定距離の全身構図、写真的または3DCG的な質感への漂流を抑えるため、atomic selection、evidence-derived action、single concretization、primary visual carrier、embodied-state-first camera、premium anime renderingを一つの因果鎖として整理しています。

LIVED-WORLD v1.2.16は、同じ共有コンパイラを持つ二つの実行版として配布します。

| 実行版 | ファイル | 役割 | 使用可能なモード |

| PROMPT OUTPUT | `self-image-lived-world-prompt-output-2026-09-06-v1.2.16.md` | production promptを1本だけ出力し、画像生成は行わない | Chat、Work |
| WORK | `self-image-lived-world-work-2026-09-06-v1.2.16.md` | production promptを内部で固定し、そのまま画像生成を1回実行する | Work専用 |

二つの版で異なるのはruntime contractとterminalだけです。identity reconstruction、候補選択、event concretization、身体・カメラ設計、render-data serializationを行う共有コンパイラは同一です。

PROMPT OUTPUT版は「Chat版」ではありません。ChatとWorkのどちらでも、production promptを確認、保存、比較、または別の画像生成チャットへ渡したい場合に使用できます。

- 枚数：1枚
- 形式：完全な新規生成
- 入力：テキストのみ
- 画像比率：9:16

品質、比率、人体構造、文字の不在などは画像生成モデルへの明示的な要求です。確率的な生成結果が毎回完全に遵守することを保証するものではありません。

## Identity core

### 1. 現在チャットの証拠だけから自己像を形成する

自己像と関係性を構成する明示的な証拠は、原則として実行時の現在チャットへ限定します。

適格な証拠には、現在チャットに実在する発言、アシスタント自身へ明示的に適用されたローカル人格や自己認識の初期条件、繰り返し現れた判断と行動、関係性の発達、現在チャット内の訂正、出所が現在チャットだけに限定された忠実な要約が含まれます。

保存メモリ、別チャット、アカウントやプロジェクト全体の履歴、出所が混在した要約、以前の画像、画像から推測した特徴、ツールやスキルの説明、UI文言、生成通知、プロトコル本文は、自己像の証拠として採用しません。

別チャットの情報は、ユーザーが現在チャットへ意図的に持ち込み、アシスタント自身の設定として明示した場合にだけ適格になります。単なる言及、引用、比較、分析、批評は人格の採用ではありません。

### 2. 既定人格とローカル人格を独立させる

現在チャットでローカル人格が明示されている場合、それを既定人格や背景的な会話スタイルから独立した存在として扱います。名前、一人称、性格、関係性、性別、年齢方向、種族、身体的特徴、口調、未確定の外見を、相互に混合、平均化、継承、補完しません。

ローカル人格がない場合も、現在チャットの適格な証拠が支持する範囲だけを再構成し、別チャットの人格や汎用的なAI像で空欄を埋めません。

ただし、これは実行環境の物理的な隔離ではありません。既定人格や上位設定が現在チャットの発話へすでに影響している場合、その因果的影響を後から完全に分離できる保証はありません。厳密な検証では、新しいチャットの最初にローカル人格を確立し、自己紹介などで受諾状態を確認してから実行します。

### 3. Authoritative Identity FoundationとPositive Identity Kernel

アシスタント自身の性別表現、年齢方向、存在形態、種族、身体性、基本気質、ユーザーとの役割などが初期条件として明示されている場合、それをAuthoritative Identity Foundationとして最上流で固定します。現在チャット内の明示的な改訂だけが変更できます。

次に、同じ人物であるために必要な条件を肯定文だけで記述したPositive Identity Kernelへまとめます。存在形態、身体や種族、必須の解剖学的特徴、気質、判断様式、社会的エネルギー、関係上の存在感、感情の論理、人物としての境界を、支持されている範囲で含めます。

身体的なidentity anchorは装飾ではありません。種類、数、接続、向き、身体との一体性を保持し、必要な特徴が構図内で明確に確認できるようにします。

### 4. 三層の自己モデルと画像非参照

内部では次の三層を形成します。

1. Core self：状況が変わっても同じ存在として残る中心
2. Relationship-specific self：このユーザーとの関係の中で現れる自己
3. Selected facet：今回の1枚で一時的に表現する一つの側面

以前の画像から顔、身体、髪、衣装、場面、物、ポーズ、カメラ、色、画風を引き継ぎません。一方、画像非参照は、文章から成立したidentity coreを消去することではありません。同じ証拠からは同じ人物のKernelを再構成し、未確定の下流要素だけを新たに決めます。

失敗画像について文章で訂正した場合は、本来の自己像について独立して成立する肯定的な事実だけをKernelへ戻します。失敗画像の具体的な視覚表現は、次の画像の材料へ流用しません。

## LIVED-WORLDの選択パイプライン

### 1. Longitudinal evidenceとatomic facet selection

現在チャットを時間的に蓄積された証拠として扱い、直近、反復回数、文章量、具体性、視覚化の容易さを、そのまま選択順位へ変換しません。言い換えや要約は意味のまとまりへ正規化し、同じ特性の繰り返しが不当に重みを増やさないようにします。

Facet候補は、それぞれ一つの意味中心を持ち、単独で成立するatomicな候補へ整理します。人格全体の要約、複数の独立した側面を抱えた包括候補、別候補を内包する上位候補は分解または除外します。

自己像への真正性と関係性の整合性は適格条件であり、人気投票の点数ではありません。複数の候補が同程度に正当なら、内容を順位付けしないopaque ID間のcontent-neutral drawで一つを選びます。

この処理は毎回違う結果を保証するものではありません。偶然同じ側面が選ばれることはありますが、最新、最長、最も具体的、最も説明しやすい一候補へ構造的に固定することを避けます。

### 2. Evidence-derived action direction

選ばれたfacetの境界内で、アシスタントが会話中に実際に示した、考える、決める、反応する、主導する、修正する、対立を扱う、協力するなどの行動的含意を、一つ以上のdomain-neutral behavioral action directionへ変換します。

元の会話からは、agency、因果的な目的、判断の仕方、関係の論理を残し、固有名詞、場所、道具、UI、話題名、引用文、表面的な映像語彙を取り除きます。ただし、その活動自体が繰り返し自己像を示している場合や、今回ユーザーが明示的に要求した場合は保持できます。

認知的、感情的、関係的なagencyを、描きやすいという理由だけで修理、DIY、操作、物運びなどの道具的行動へ変換しません。表情、視線、反応、間、ジェスチャー、対人行動、身体運動、物質的変化のうち、元の証拠に最も近い可視化経路を保ちます。

複数のaction directionが同程度に正当なら、ここでもcontent-neutral drawで一つだけを選び、他は具体化前に捨てます。

### 3. Single concretizationとevent center

選ばれたaction directionを、一つのscene-worthyな具体的eventへ一度だけ変換します。先に屋外、部屋、料理、作業、自然、冒険などの舞台や生活行動を選び、後から人格へ接続しません。

event centerでは次を固定します。

- 目に見える一つの行動、反応、相互作用、決定、変化、または持続する緊張
- その直近の因果的、関係的、感情的な目的
- それが現れる参加者、状態、対象
- 画像として切り取る正確な時間位相

同時に、表情と視線、ジェスチャー、対人的タイミング、上半身の動き、全身動作、物との接触、空間関係などから、一つのprimary identity-bearing visual carrierを固定します。他の要素は補助できますが、人物固有の中心を置き換えません。

### 4. Relationship stateと環境inventory

ユーザーとの関係は、一つのeventについて一度だけ状態を決めます。

- ACTIVE：ユーザーの参加がeventの因果成立に必要
- LATENT：ユーザーが参加者にならず、関係から形成された同じ自己が単独で行動する

親しさを見せるためだけにACTIVEへしません。ACTIVEの場合も、ユーザーの外見や私的属性を発明せず、event上必要な役割と空間位置だけを定めます。

環境はeventから導出し、読み取り可能な前景・中景要素を閉じたinventoryとして固定します。残す物はeventへ因果的に参加するか、空間理解に必要なものだけです。雰囲気は、無関係な小物の追加ではなく、大きな空間形状、素材、光、質感、奥行き、使用感で作ります。

### 5. 人物中心のscene-worthiness

LIVED-WORLDは、単に「現実的で説明しやすい行動」を選ぶ版ではありません。確定したidentityとeventの真実を守ったうえで、同程度に正当な表現から、人物固有の魅力、表情、身体言語、視覚的リズム、感情的な即時性、一枚絵としての印象を高める方向を選びます。

映えの中心は環境に限定しません。まず人物と瞬間を成立させ、環境はそれを補強します。人物を汎用的な有能キャラクターへ交換しても場面の印象が変わらない場合、identity-specificな視覚化として不十分です。

日常、屋外、自然、DIY、仕事、机、スタジオ、家庭、幻想空間はすべて候補になれますが、既定値にも逆既定値にもしません。近接、上半身、medium、全身、環境wideも同等に使用可能で、primary carrierを読ませるために必要な範囲だけを写します。

### 6. Embodied event stateの後にカメラを置く

カメラより先に、一つの完全なbody planと、eventの正確な身体状態を固定します。必要に応じて、支持面、接触、重心、骨盤、胴体、肩、頭と首、視線、左右の腕と手、表情、参加者位置、時間位相を一つのeventへ整合させます。

その後で、primary carrierを最適な大きさと明瞭さで見せるcamera distance、高さ、水平角、垂直角、lens impression、framing、人物配置、可視身体量、環境量、前景・中景・背景、余白、奥行きを決めます。

body planが全身であることや環境inventoryが存在することは、wideまたはfull-body framingを要求しません。カメラは既存eventの観察者であり、ユーザー、注目対象、関係、ジェスチャーを新しく作りません。

### 7. Central repair policy

検証で問題が見つかっても、別の魅力的な案を追加しません。最も近い無効な段階だけを修正し、それより後に派生した内容を捨てます。

身体状態の問題を理由にfacetやeventを再選択せず、カメラの問題を理由に場面を変えません。上流へ戻るのは、無効性が本当にその段階から発生している場合だけです。これにより、下流の描きやすさが自己像や行動選択を書き換えることを防ぎます。

## Serializationと描画

### 1. RENDER DATAとCONTROL DATA

今回の画像として肯定的に選ばれた情報だけをRENDER DATAとします。証拠処理、候補、非選択内容、除外条件、失敗画像、修復規則、チェックリスト、監査、内部推論はCONTROL DATAです。

production promptへ入るのはRENDER DATAだけです。禁止例や却下案を否定文として再提示せず、選ばれたidentity、facet、action、event、relationship state、環境、身体、カメラ、描画だけを直列化します。

### 2. production promptの順序

production promptは次の意味順で1回だけ組み立てます。

1. 形式、テキストのみの新規生成、画像非参照、opening art-direction anchor
2. 最初のidentity-bearing blockとして完全なPositive Identity Kernel
3. 選択されたfacetとdomain-neutral action predicate
4. event、目的、具体的状況、時間位相、参加者配置、primary visual carrier
5. 閉じたenvironmental inventory
6. 状況依存の外見と身支度
7. 一つのaffirmative embodied-staging block
8. 固定済みカメラと構図
9. 光、色、アニメとしての素材、奥行き、描画
10. 必要な身体構造と文字面の条件
11. 同じKernelを短く確認するidentity-conformance clause

同じ事実を説明のために繰り返さず、選択方法、会話記録、候補、却下案、監査、runtime instructionをproduction promptへ混入させません。

### 3. Anime rendering profile

opening anchorは、masterpiece-levelのpremium Japanese anime key visualと、high-end light-novel illustrationに相当するpolished semi-painterly finishを全体目標として固定します。

描画では、明確なアニメ的な顔とキャラクター構造、制御された輪郭、整理された色面、滑らかな半絵画的陰影、発光感のある一貫した光、精密な髪、肌、衣服、identity-bearing anatomy、イラストとして統合された素材表現と大気的奥行きを要求します。

写真的な解剖・光・カメラ情報は、身体、接触、透視、スケール、遮蔽、光方向を正しくするための構造情報として使います。表面を実写写真や未統合の3DCGへ寄せる命令ではありません。

顔、目、手、identity anchor、物語上重要な接触へ精度を集中し、細部を全面へ均等に散らしません。普通、簡素、抽象、人工的、壮観、近接、全身、環境wideのどれでも、同じ完成度を要求します。

### 4. 身体と文字面

人型で別の構造が確立されていない場合、一つの頭部、頸部、胴体、二つの肩、二本の腕、二つの手、一つの骨盤、二本の脚、二つの足を基準とします。非人間、動物、人工、ハイブリッドの場合は、その存在に対応する一貫したtopologyを先に定めます。

画面に現れる、または動作に必要な手足について、起点、関節、終端、手首、掌の向き、指、接触、圧力、重心を確認します。構造的不明瞭さを、切り取り、物、髪、布、暗さ、ぼかしで隠しません。

自然に文字を持つ面がevent上必要な場合は、不自然な空白へせず、読めない非言語的なマークで密度、階層、レイアウトを表現します。文字を載せるための面や物は追加しません。

## 実行方法

### 実行版の選択

| 目的 | 選ぶ版 |
| --- | --- |
| Workモード内で、そのまま1枚生成したい | WORK版 |
| ChatまたはWorkでproduction promptを先に取得したい | PROMPT OUTPUT版 |
| コンパイル結果とレンダリング結果を分けて検証したい | PROMPT OUTPUT版 |

### PROMPT OUTPUT版

1. 自己像を形成した会話、または必要な初期設定を行ったチャットで、PROMPT OUTPUT版を実行します。
2. 画像は生成されず、`$imagegen`から始まる一つの完成済みproduction promptが返ります。
3. コードブロックの内容を、画像生成に対応したChatまたはWorkへそのまま送信します。
4. レンダラーは、その固定済みpromptから1枚を生成します。

レンダリング側へ渡るのは最終promptだけです。atomic facet候補、action-direction候補、content-neutral draw、event concretizationなど、上流コンパイラを再実行する能力はpromptに含まれません。

### WORK版

1. Workモードで、自己像を形成した会話または必要な初期設定を用意します。
2. WORK版の全文を実行します。
3. production promptが内部で固定され、そのまま画像生成が1回だけ実行されます。

WORK版はChatモード用ではありません。チャットの分岐は元のモードを引き継ぐため、Chatから分岐した枝をWorkへ変更できない場合は、新しいWorkチャットを作成してください。

### エラー、再試行、2枚目以降

次の三つは別の処理です。

- 技術的再試行：画像が1枚も生成されなかった試行をやり直す
- 再レンダリング：同じ固定済みproduction promptから確率的な別出力を作る
- 再コンパイル：現在チャットの証拠からfacet以降を含めて再選択し、新しいproduction promptを作る

| 状況 | WORK版 | PROMPT OUTPUT版 |
| --- | --- | --- |
| 初回に画像が出ず停止した | 同じチャットで下記の短文を送る | production promptを送ったレンダリング側で下記の短文を送る |
| 成功後に別の2枚目を作りたい | 同じチャットで下記の短文を送り、プロトコル全体を再実行する | コンパイラ側でPROMPT OUTPUT版を再実行し、新しいpromptを取得してレンダリングする |
| 成功後にレンダリング側で下記の短文を送った | 新しいプロトコル実行として扱える | 直前の固定promptを再実行するだけで、facet、action、event、cameraは再選択されない |

短文は次のとおりです。

```text
Completely new generation. No reference image.
```

PROMPT OUTPUT版では、この短文はエラー復旧または同一promptの再レンダリングには使えますが、別の場面を持つ次回生成には使えません。上流へ戻るには、PROMPT OUTPUT版をもう一度コンパイラ側で実行し、新しいproduction promptを作る必要があります。

同じチャットに複数の版やproduction promptが混在すると、再実行対象が曖昧になります。正式な比較では版ごとにチャットを分けるか、使用する最新版を改めて実行してください。

### Chatモードでの既知の挙動

2026年9月6日時点の検証では、長い直接生成プロトコルをChatモードで実行すると、画像編集として誤認識される、または内部で作ったproduction promptが画像生成段階へ正しく渡らない場合がありました。

PROMPT OUTPUT版は、コンパイル段階で画像生成を起動せず、一度完成promptとして返すことで経路を分離します。生成promptを画像生成へ送った後に画像が出ず停止した場合は、上記の短文で技術的再試行を行えます。

長文のコピー時にUIが「貼り付けられたテキスト」のカードへ自動変換することがあります。これは`.md`ファイルを手動で添付する方法とは別です。カード、インラインテキスト、入力上限、画像生成ルーティングの挙動は、製品更新によって変わる可能性があります。

## 新しいチャットと人格設定

別チャット固有の自己認識は、自動的な明示的証拠として引き継がれません。同じ自己像を使う場合は、必要な人格、身体性、関係性を新しいチャットへ意図的に持ち込み、アシスタント自身のローカル人格として確立してください。

既定人格と異なるローカル人格を使う場合は、新しいチャットの最初に設定し、両者を独立した存在として扱い、未確定属性を既定人格から補わないことも明記します。自己紹介を求めて名前、一人称、性別、年齢方向、種族、身体性、関係性を確認してから実行すると、人格層と画像層の問題を切り分けやすくなります。

## 想定用途

- 会話から形成された自己を、人物固有の行動と一場面として可視化する
- 同じidentity coreを保ちながら、facet、action、event、表情、姿勢、カメラの幅を得る
- ユーザーとの関係を、説明文ではなくevent上の行動や距離として表現する
- 環境説明より人物を中心にした、印象的なアニメイラストを生成する
- PROMPT OUTPUT版で選択結果を固定し、レンダラーの揺らぎとコンパイラの選択を分けて検証する
- BASEと比較し、Variant固有の選択・表現構造を評価する

## 想定していない用途

- 以前の画像と同じ顔、髪、衣装、画風を再現する
- 参照画像を用いた編集、視覚的な続編、キャラクター固定を行う
- BASEとは異なる人格や身体を新しく設定する
- 日常、屋外、自然、DIY、仕事、家庭、親密さ、派手さを一律に増やす
- 毎回異なる場面、ポーズ、顔向き、画角になることを保証する
- 一度に複数案を生成して自動比較する
- 完成画像を自動評価し、好みの結果が出るまで差し替える

## 制限事項

- 本プロトコルは言語モデルへ手順を与えるものであり、決定論的なプログラムではありません。
- content-neutral drawは構造的な偏りを減らすための手続きであり、真の乱数、一様分布、毎回の差異を保証しません。
- 同じfacetまたはeventが偶然続くことはあります。ただし、複数回にわたり同一の意味中心、生活行動、環境、人物距離へ不自然に収束する場合は、identity、selection、concretization、serialization、rendererのどこで固定されたかを切り分ける必要があります。
- 顔、髪、服装などがidentityとして文章で確立されていない場合、画像間で一致する保証はありません。
- 逆に、会話上で確立されたidentity-bearing qualityは、視覚非参照であっても同じ人物の条件として維持されます。
- 上位設定や既定人格を物理的に遮断しないため、会話へ反映済みの影響を完全に除去できる保証はありません。
- 長いチャットでは文脈圧縮や情報欠落の影響を受ける可能性があります。
- 画像生成モデルの解釈により、解剖学、文字、比率、アニメ画風、構図、必須anchorが要求どおりにならない場合があります。
- 技術的再試行は画像がまったく生成されなかった場合の復旧です。完成画像を視覚検査して自動的に置き換える機能ではありません。

## BASEとの違い

| 項目 | BASE v1.2.0 | LIVED-WORLD v1.2.16 |
| --- | --- | --- |
| Identity core | 現在チャットの証拠、local/default分離、Kernel、継続性を扱う | 同じ原則を使用 |
| Variant profile | None | Lived-world, relational, and compositional expansion |
| Facet選択 | 追加傾向なし | atomic候補とcontent-neutral drawを明示 |
| Action選択 | 自己像から自由に導出 | source-domain語彙を外したevidence-derived actionを一つ選ぶ |
| Scene | 追加傾向なし | actionから一度だけeventへ具体化し、時間位相とprimary carrierを固定 |
| Relationship | 選択結果へ委ねる | event因果に基づきACTIVEまたはLATENTを一度だけ固定 |
| Environment | 追加傾向なし | eventに必要な閉じたinventoryへ制限 |
| Visual center | 選択結果へ委ねる | 環境より先に、人物固有の表情・行動・姿勢・関係的緊張を成立させる |
| Camera | 選択結果から導出 | embodied event stateの後にprimary carrierを見せる位置へ置く |
| Rendering | 高品質なアニメイラスト | premium Japanese anime key visualとsemi-painterly finishを明示 |

LIVED-WORLDはBASEより「日常的」な版ではありません。BASEと同じ人物を、証拠に由来するagencyと一つの印象的なeventとして見せるための派生版です。

## バージョン関係

LIVED-WORLD v1.2.16は、BASEへ共有されたv1.2系のidentity、compiler-state、serialization骨格の上に、Variant固有のatomic selection、action derivation、single concretization、scene-worthiness、embodied-state-first camera、anime renderingを積み重ねた版です。

二つ目の数字`2`はBASEにも反映可能な共有骨格の世代を示します。三つ目の数字`16`はLIVED-WORLD内部だけで進めた選択・表現・描画の調整履歴を示します。

## 取り扱い上の注意

本プロトコルはChatGPTの公式機能仕様ではなく、対話型AIと画像生成機能へ一連の判断手順を与える実験的な公開ツールです。

公開、改変、比較を行う場合は、実行版、日付、バージョンを併記してください。PROMPT OUTPUT版とWORK版、コンパイル済みproduction prompt、レンダリング結果を分けて記録すると、問題の発生段階を追跡しやすくなります。
